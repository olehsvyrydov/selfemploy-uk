What the nightly e2e run is measured against.

  broken  The number of e2e-tagged tests known to be failing. The run fails only if the count
          exceeds this, so the suite cannot rot further while it is being repaired.
  tests   How many tests a whole-suite run produces. Checked as well as the failure count, because
          a run that never happened reports zero failures and would otherwise look like a clean
          sweep. A count far above it means reports from an earlier run are being counted too.

Measurements on 2026-07-28, all of the same commit, all 883 tests:

  75   CI, once Xvfb had a window manager
  76   developer desktop
  77   developer desktop, a second run

One of those 75 has since been deleted rather than fixed: it saved records, reset the in-memory
database, and asserted the records were still there, which cannot happen. Real coverage of the same
claim now lives in SubmissionPersistenceTest, against a file. So the totals drop by one to 882 tests
and an expected 74-75 broken, and this baseline drops to 76 - the same one-test headroom over the
highest expected reading.

`broken` is the highest of those, not the lowest. Two runs of the same tree in one environment
differed by one, so at least one test is flaky, and a ratchet that trips on a coin flip gets ignored
like any other false alarm - which is how this suite reached its current state. Calibrating to the
CI figure alone would also make the script fail on a clean checkout locally, where it is the obvious
thing to run before pushing a fix. Finding the flaky test would let this drop to 75.

For the record, before the job ran a window manager the same commit reported 224 broken on xvfb-run
defaults and 225 with 24-bit colour. None of that difference was the tests: without a window manager
a stage never takes focus, so TestFX finds no nodes. Never calibrate this from a broken display.

Lower `broken` in the same commit that fixes tests. Never raise it.
